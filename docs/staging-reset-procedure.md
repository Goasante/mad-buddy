# Staging rebuild-from-zero procedure

**Status: awaiting owner approval. Not executed.**

This is the only convincing proof that
`20260903120000_service_role_grant_reproducibility.sql` closes the defect.
Applying it to the *current* staging database proves nothing — that database was
already repaired by hand, so the grants are present either way.

## What this destroys

Everything in the staging Postgres database and its auth store:

- 100 synthetic `staging-user-NNN` accounts
- 100 profiles, 302 friendships, 3 conversations, 486 messages
- 2 media assets (the generated PNG and WAV)
- all applied migration history on that project

All of it is regenerable by `npm run seed:staging -- --apply`. **No human data
exists on this project** — every profile was verified synthetic (0 non-synthetic
rows).

## Procedure

Every step runs from the staging worktree, which is linked to staging only.

### 0. Re-assert the target (mandatory)

```bash
cd /c/mb-staging-data
REF=$(cat supabase/.temp/project-ref)
[ "$REF" = "ivaydmciwmjdjsrovbqb" ] || { echo "HARD STOP"; exit 1; }
[ "$REF" != "cabkhxxnrybzhkbtoiiz" ] || { echo "HARD STOP: PRODUCTION"; exit 1; }
```

The link file is tracked in git and reverts to the **production** ref on
`git checkout` — this is the PR #15 footgun, and it is why the check is
repeated immediately before the destructive call rather than trusted from
earlier in the session.

### 1. Reset the remote database

```bash
npx supabase db reset --linked
```

Destroys all objects and replays migration history from zero.

### 2. Bring in the repair migration

The fix lives on `fix/fresh-db-service-role-grants` (commit `17a25d3`), not on
`main`. Either cherry-pick it into the staging worktree, or run the reset from a
worktree that contains it. Migration count becomes **125**.

### 3. Prove the defect is closed — before any manual SQL

This is the whole point. **Do not run any grant SQL by hand.**

```bash
node scripts/probe-staging.mjs   # expect HTTP 200, not 42501
```

Then confirm the grant counts directly:

```sql
select count(*) from information_schema.role_table_grants
where table_schema='public' and grantee='service_role' and privilege_type='SELECT';
-- expect ~191, previously 31
```

And confirm the browser roles did **not** widen:

```sql
select grantee, count(*) from information_schema.role_table_grants
where table_schema='public' and grantee in ('anon','authenticated')
  and privilege_type='SELECT' group by grantee;
-- expect anon=3, authenticated=4 (unchanged)
```

If `anon` or `authenticated` grew, **stop** — the migration is too broad.

### 4. Verify Realtime

```sql
select tablename from pg_publication_tables
where pubname='supabase_realtime' and schemaname='public';
-- expect messages, conversation_presence, conversation_message_pins,
--        chat_polls, chat_poll_votes
```

### 5. Seed, with no hand-applied grants

```bash
node scripts/seed-staging.mjs --apply
```

Expect 100 created / 0 reused, 302 edges, 486 messages, 1 attachment, 1 voice.

### 6. Prove idempotency

```bash
node scripts/seed-staging.mjs --apply   # expect 0 created / 100 reused
```

Counts must be unchanged: 100 / 302 / 3 / 486.

### 7. Prove isolation

```bash
node scripts/prove-isolation.mjs
```

### 8. Redeploy Preview

Only needed if the anon key rotated — it does not on a database reset.

## Success criteria

```
migrations         125 applied / 0 pending
manual grant SQL   NONE
service_role API   200 (was 42501)
service_role SELECT ~191 / 191   (was 31)
anon SELECT        3   (unchanged)
authenticated SELECT 4 (unchanged)
Realtime           5/5
seed               100 users, 486 messages
seed rerun         idempotent
isolation          staging ≠ production, 0 non-synthetic rows
```

Meeting all of these is what makes the database environment reproducible.

## If it fails

Do not hand-patch and declare success — that recreates the exact blind spot
being fixed. Capture the failing grant matrix, correct the migration, reset, and
run again from zero.
